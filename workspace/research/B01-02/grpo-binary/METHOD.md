# Implementation and optimization definitions (precheck stage)

A local search, including source ignored by .gitignore, found no existing GRPO implementation; TRL/vLLM/datasets were not installed. We reuse verified Transformers/PEFT loading, the earlier prompts, and strict scoring, and implement an auditable two-GPU GRPO loop. Mathematical definitions follow the [official TRL v0.16.1 GRPO documentation](https://huggingface.co/docs/trl/v0.16.1/grpo_trainer). We do not use the TRL Trainer directly.

Each example has 8 candidates, with advantage=(binary reward−group mean)/(within-group sample standard deviation+1e−4). All-0/all-1 groups have advantage 0 and are retained. Loss is averaged over valid output tokens within each response, then equally over candidates. Actual EOS is included; prompt and padding are excluded. Incorrect responses are neither discarded nor rewarded only for correct prefixes. Each of two ranks processes 8 examples×8 candidates; DDP averaging gives an equally weighted update over all 16 examples×8 candidates.

The reference is the same frozen original model with LoRA disabled. The KL estimator is exp(logp_ref−logp_policy)−(logp_ref−logp_policy)−1. Each fresh rollout batch receives one optimizer update (μ=1). The old policy is the pre-update policy, implemented using current logp.detach as old logp. Clip ε=0.2 remains in the objective, but with μ=1 the ratio has forward value 1 and clipping does not actually truncate this batch update. This is not a multiepoch PPO-style trust-region constraint. Actual drift is monitored through KL, gradient norms, and training curves.

Candidate precheck configuration: LoRA r16/alpha32/dropout0 across seven projection types; a BF16 base with FP32 trainable adapter master weights and AdamW states, without quantization; lr1e−5 with 5-update linear warmup followed by a constant rate, β0.04, and gradient-norm clipping 1. Sampling uses temperature1/top_p1/top_k0. The full-response cap remains 256, and greedy evaluation is unchanged. Main parameters must be written to config/frozen.json after prechecks and recovery checks, without selecting configurations based on whether NAME leads.

Checkpoints contain the adapter, optimizer, each rank's CPU/CUDA/Python RNG states, and update count. step0 includes paired initialization hashes. Validation and test baselines are generated from the same original weights with adapters disabled. Seeds reference the same step0 outputs rather than presenting them as additional independent replications.

The frozen main configuration uses precheck-v2: torch.use_deterministic_algorithms(True) and CUBLAS_WORKSPACE_CONFIG=:4096:8, with other candidate hyperparameters unchanged. v1 recovery checks showed backward/update numerical differences. In v2, sampling sequences and rewards match exactly after recovery in both conditions, with an elementwise final-adapter difference of 0. Original failures are retained; settings were not chosen by NAME's lead. All six main runs are freshly initialized from the original model.

Precision details: there is no additional AMP autocast. In PEFT 0.15.2, Linear.forward casts LoRA branch inputs to the adapter-weight dtype. Frozen base linear/attention operations therefore use BF16, while LoRA branch parameters and matrix computation use FP32; merged outputs are cast back to the base dtype. Adam states are FP32. BF16 LoRA here means mixed-precision training with an unquantized BF16 base plus LoRA, rather than BF16 computation in every trainable branch. Both conditions use the same implementation.

Example order is a single deterministic seed-specific shuffle of the 4096-example training pool. Each run's 100×16 budget uses the first 1600 examples without within-run repetition. STEP and NAME have identical example-by-example order for the same seed. 4096 is the available pool size; 100 updates do not constitute a full training epoch.
