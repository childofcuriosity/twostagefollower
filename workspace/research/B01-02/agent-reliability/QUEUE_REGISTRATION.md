# Sequential workflow extension (registered before model runs)

The previous multi-file tasks can be completed in one batch. Their requirement count does not establish a long action horizon. Add a local shipment-ticket delivery workflow with sequentially released source inputs. This is a controlled synthetic workflow, not a production-agent benchmark.

One ticket is available at a time; next_ticket reveals its ID, name, filters and source path. The agent reads records, writes an aggregate report, delivers it through submit_ticket, then requests the next ticket. Delivery acknowledges receipt only: no truth-based correction, hidden score, or stop prohibition is provided. Incorrect JSON or values are accepted as a delivery and independently scored afterward. The agent may finish at any time. Therefore the workflow does not externally force continued work or guarantee correct results. Filesystem tools and Python remain available; reusable helper code is allowed.

Development: two four-ticket instances, seeds 20262001/2. Main frozen instances: 12 tickets × three seeds 20262101–3 and 24 tickets × three seeds 20262201–3. All four conditions plan/reminder/identity/todo use the same native runtime, deterministic model, tasks and budget. The initial user states total ticket count and completion criteria; each ticket's specific values become available only upon release. IDs are provided in normal task payloads in all conditions; identity group additionally recites ID and name. Report true completion, delivered count, correctly delivered count, unstarted tickets, incorrect reports, voluntary final response versus budget exhaustion, tool errors, tokens, turns and costs. Do not label wrong arithmetic as early abandonment.

Development must demonstrate basic four-ticket capability before main evaluation. Budgets: 32 turns/8192 generated tokens for four-ticket development; 128 turns/24000 generated tokens, 30000 context and 2400 seconds for main. These higher limits reflect the explicitly longer interaction horizon, shared across groups. No task thinning after outcomes. If baseline already solves all tasks, report a ceiling and do not claim identity benefit. Meaningful completion improvement in prior tasks remains an engineering finding until protocol components and external validity are separately tested.
